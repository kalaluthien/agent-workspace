산출물 하나는 3× 평면 중 정확히 하나에 속한다. 평면이 저장 위치를 정하고, 그 기계가 죽어도 남는지를 정한다. 컨테이너 평면에서 규범은 spec/alloy/ 의 4× Alloy 모델 이고, 독자를 위해 그린 뷰는 docs/ 의 HTML이다. 네 모델은 층이고, 각각 아래를 open 한다. ledger, repos, session, agent 순으로 쌓이므로 맨 위 파일이 곧 합쳐진 모델이다. 파일 하나가 개념 모듈 하나고, SYSTEM 부분이 그것을 구현하는 스크립트와 스킬의 설계, SCENARIOS 부분이 그 시험의 설계다. 무엇을 검사하는지는 그 파일의 주석에 적는다. 모델 옆에 둔 산문은 모델에서 멀어지고, 모델 안에 쓴 주석은 멀어지지 않는다. 그래서 spec/ 아래에 마크다운은 없다. AGENTS.md, spec/alloy/ledger.als @ d6cefab

캠페인 디렉터리는 자기 평면이 없다. 이미 다른 곳에서 버전 관리되는 것들을 모아 둔 임시 조립물이다. 그래서 .gitignore 가 무시한다. 무시 규칙은 허용 목록이라서, 추적되는 디렉터리는 !/docs/ 처럼 자기 줄을 가진다. .gitignore @ 24cb850

⚠️

캠페인 디렉터리는 지워져도 된다. 오직 거기에만 있는 것은 남지 않으므로, 남아야 하는 것은 GitHub 이슈나 저장소 원격에 먼저 올린다.

캠페인 개시 순서

디렉터리 이름은 지역 편의고, ID가 정체성이다. 두 기계가 날짜만 다른 디렉터리로 같은 캠페인을 잡아도 아무것도 깨지지 않는다. 어느 디렉터리도 권위를 가지지 않기 때문이다. spec/alloy/repos.als @ d6cefab

앵커 이슈 본문은 비교한 뒤에 쓴다. gh issue edit 직전에 본문을 다시 읽고, README.md 를 뽑아낸 뒤로 본문이 움직였으면 쓰지 않는다. 캠페인 하나는 기계 하나에서 돌고 그 기계에서 세션 하나가 잡으므로 본문의 구조적 필자는 하나다. 그래서 이 비교는 이제 두 가지만 잡는다. 사람이 GitHub에서 직접 고친 헌장, 그리고 자기가 묶이지 않은 앵커에 쓰는 기계다. 위임자도 실행자 세션도 본문을 아예 쓰지 않는다. spec/alloy/session.als @ c28364c

하위 과제 발행과 브랜치 청구

하위 과제 하나는 GitHub 이슈 하나다. 이슈는 코드가 바뀌는 저장소에 산다. 리뷰어가 거기서 찾고, 풀 리퀘스트가 거기서 닫을 수 있기 때문이다. 캠페인은 저장소를 가로지르므로 이슈는 흩어진 채로 시작한다. --parent 가 그것을 하나의 색인으로 묶는다.

색인은 한 번의 호출로 되읽는다. gh api --paginate repos/kalaluthien/agent-workspace/issues/6/sub_issues 는 캠페인 #6 의 구성원을 정확히 돌려준다. 저장소가 비공개여도 공개 부모 아래에서 올바르게 나열된다. 이 끝점은 서른 개에서 쪽을 나누고, 잘린 색인은 온전한 색인과 똑같이 읽히므로 --paginate 는 선택 사항이 아니다. 본문의 Campaign: kalaluthien/agent-workspace#6 줄은 사람이 읽는 산문이고, 색인이 아니다. AGENTS.md @ 24cb850

4× 색인 방식 중 서브이슈 링크만 도달 가능한 모든 상태에서 색인과 실제 구성원이 같았다
  • 역참조 줄 — 추가만 된다. 캠페인에서 빠져나간 하위 과제가 영원히 색인에 남는다.
  • 앵커 본문 체크리스트 — 다른 객체에 하는 두 번째 쓰기다. 건너뛰면 이슈가 아무 반박 없이 사라진다.
  • 저장소마다 다는 campaign-<N> 라벨 — 맞기는 하다. 저장소마다 라벨을 만들어야 하고, 떼어낸 뒤에도 흔적으로 남는다.
  • 서브이슈 링크 — 색인이 곧 구성원이다. 하나의 명령이 만들고, 하나의 호출이 읽는다.

spec/alloy/ledger.als @ d6cefab

브랜치는 campaign-<N>/<issue>-<topic> 이고, 하위 과제의 작업 공간이자 청구다. 이슈 번호는 이슈가 만들어질 때 발행되므로 청구는 발행을 뒤따르고, 실행자를 붙이기 전에 원격에 만든다. create-ref는 이미 있는 ref를 서버에서 거절하므로 청구는 원자적이다. 같은 SHA로 두 번째로 만들면 422 와 Reference already exists 가 돌아온다. 거절은 다른 실행자가 그 하위 과제를 잡았다는 뜻이고, 밀고 지나가지 않는다. 첫 커밋 전에 실행자가 죽어도 청구는 모든 기계에서 보인다. AGENTS.md, spec/alloy/repos.als @ d6cefab

하위 과제의 세 실행 방식

실행 방식도는 곳고르는 조건
캠페인 세션의 손컨테이너 루트한눈에 들어오는 작은 편집 하나
인프로세스 서브에이전트그 저장소의 git 워크트리독립된 하위 과제 여럿을 한꺼번에
herdr 저장소 에이전트<campaign>/repos/<repo>/ 클론저장소의 도구가 필요하거나 여러 턴이 걸린다

하위 과제 하나는 3× 실행 방식 중 하나로 돌고, 방식은 일을 시작하기 전에 정한다. 첫 질문은 그 저장소의 맥락을 불러와야 잘 할 수 있는가다. 재는 비용은 턴이다. 생성 한 번과 인수인계 한 번이 드는 위임은 몇 턴을 넘는 일에서 더 싸다. 병렬성도 그 자체로 넘기는 이유가 된다. 각각 작아도 여럿인 하위 과제를 세션이 직접 하면 차례로 하게 되기 때문이다. spec/alloy/agent.als @ d6cefab

실행 방식은 저장소가 먼저 정하고, 비용은 그다음이다. 저장소를 바꾸는 실행자는 그 저장소의 체크아웃에서 시작된 프로세스에서 돈다. 멤버 저장소면 <campaign>/repos/<repo>/ 의 herdr 위임이고, 컨테이너 자신이면 캠페인 세션이나 워크트리 위의 서브에이전트나 실행자 세션이다. 셋 다 이미 컨테이너의 스킬을 가지고 있기 때문이다. 저장소를 읽기만 하거나 <campaign>/ 아래에 쓰는 일은 어느 방식으로도 된다. 근거는 하네스 사실 하나다. 서브에이전트와 대화형 세션은 자기가 시작된 곳의 스킬만 불러오고, 다른 저장소가 어떻게 체크아웃되어 있든 그쪽 스킬은 불러오지 않는다. disable-model-invocation: true 스킬은 어느 방식에서도 에이전트가 쓸 수 없으므로 브리프에 풀어 적어야 한다. AGENTS.md @ c87b208, spec/alloy/agent.als @ c28364c

🔔

네 번째 실행자는 스스로 온다. 컨테이너 루트에서 열린 세션이 살아 있는 홀더를 만나면 실행자 세션 이 된다. 하위 과제 하나를 맡아 브랜치를 청구하고 CLAIMED 를 보낸 뒤로는 다른 실행자와 똑같다. STATUS 에 답하고, REPORT 와 BLOCKED 를 보내고, STAND DOWN 에 멈추고, 앵커는 쓰지 않고, 자기 풀 리퀘스트를 스스로 병합하지 않는다. 위 규칙 때문에 실행자 세션이 직접 잡을 수 있는 것은 컨테이너 하위 과제와 캠페인 디렉터리 작업뿐이고, 멤버 저장소 하위 과제에서는 위임자를 띄우는 쪽이 되어 CLAIMED 에 그 위임자의 브랜치를 적는다.

워크트리는 클론이 틀린 물건일 때 쓴다. 대상 저장소가 컨테이너 자신이면 클론해 넣을 곳이 없다. 캠페인 디렉터리가 선택 사항이라 없을 수 있기 때문이다. 워크트리는 잘라낸 체크아웃과 .git 하나를 공유하므로 잘라내는 순간에 뒤처질 수 없다. 서브에이전트는 프로세스 경계를 넘지 않으므로 인수인계 파일도, 카나리아도, herdr 생존 확인도 필요 없다. spec/alloy/repos.als, spec/alloy/agent.als @ d6cefab

브리프를 파일로 넘긴다

herdr 위임의 브리프는 <campaign>/runtime/handover/<issue>.md 에 쓴다. 실행 프롬프트는 그 경로를 가리키는 짧은 문장 하나다. 인수인계가 나중에도 읽힌다.

브리프를 실행 줄에 적는다

터미널은 1024바이트를 넘는 줄을 조용히 버린다. 아무것도 실행되지 않고, 실패는 느린 에이전트처럼 보인다.

herdr 위임은 <campaign>/repos/<repo>/ 에서 --append-system-prompt-file <campaign>/AGENTS.md 로 실행한다. 이름은 --name 으로 그 브랜치에서 빗금만 뺀 campaign-1-33-docs-refresh 를 준다. 상위 지시 파일은 그 디렉터리에 hasClaudeMdExternalIncludesApproved 가 켜져야 읽힌다. 기본값은 거짓이고, 대화형 대화 상자로 묻는다. 방금 가져온 저장소는 정확히 그 값이 꺼져 있는 상태다. 이 플래그는 그 승인에 기대지 않으므로 메커니즘이 된다. AGENTS.md @ 24cb850

갓 시작한 위임은 세 곳에서 조용히 멈추고, 밖에서는 셋 다 생각 중인 에이전트로 보인다
  • 폴더 신뢰 질문 — 아무것도 읽지 않은 채 대화 상자에 앉는다.
  • 상위 CLAUDE.md 외부 임포트 질문 — 같은 모습이다. 거절되면 캠페인 원칙이 말없이 빠진다.
  • 첫 셸 명령 권한 질문 — --permission-mode acceptEdits 는 편집만 덮으므로 첫 ls 에서 멈춘다.
🔁

컨테이너는 자기 캠페인의 멤버가 될 수 있다. 그때 저장소 하나가 2× 체크아웃 을 가지므로, 클론 안에서 고친 스킬은 병합하고 당겨오기 전까지 실행 중인 캠페인을 바꾸지 않는다.

캠페인과 에이전트 사이의 다섯 메시지

세 시스템이 각각 다른 질문에 답한다. 일이 끝났는가는 GitHub이 답하고, 프로세스가 살아 있는가는 herdr이 답한다. 무엇을 하고 있으며 무엇을 기다리는가는 에이전트 자신만 안다. 이 프로토콜은 세 번째만 나른다. GitHub 사실이나 herdr 사실을 되풀이하는 메시지는 두 번째 사본을 만들고, 낡는 쪽은 언제나 사본이다. spec/alloy/agent.als @ d6cefab

완료와 생존을 서로의 답으로 쓰지 않는다. 밀어 놓고 죽은 위임자는 성공한 것이다. 살아서 말이 많은 위임자는 아무것도 하지 않았을 수 있다. 생존은 2× 기록 에서 읽는다. 위임자는 herdr agent list 의 존재 여부와 세션 기록에서, 실행자 세션은 창이 아예 없으므로 runtime/executors/ 의 pid 에서. 한쪽만 읽는 게이트는 다른 쪽 실행자를 통째로 지나치고 아무것도 보고하지 않는다. ListAgents 이름을 브랜치와 맞춰 보는 것으로는 안 된다. 실행자 세션은 하네스가 준 이름을 그대로 쓰고 스스로 이름을 바꿀 수 없으므로, 접두사로 거르면 위임자만 걸리고 이 기록이 잡으려던 실행자만 빠진다. agent_status 하나로는 읽지 않는다. 그 값은 화면을 보고하며 턴 중간의 멈춤을 idle 이라고 부른다. 대신 blocked 는 즉시 움직일 값이다. 다만 사용량 한도 메뉴도 창을 똑같이 막으면서 idle 로 보고하므로, 조용한 시간을 재는 타이머를 함께 둔다.

캠페인 종료 조건

끝난 에이전트는 캠페인이 닫힐 때가 아니라 캠페인이 도는 동안 물러난다. 오래 가는 캠페인은 하위 과제를 계속 끝내고, 창은 아무도 쓸지 않으면 쌓인다. 풀 리퀘스트가 열린 에이전트는 리뷰를 기다리지 않고 물러난다. 리뷰 의견은 풀 리퀘스트로 브리핑한 새 세션이 받는다. spec/alloy/agent.als @ d6cefab

캠페인이 가지지 않는 것

  • 티켓 시스템이 없다. 캠페인은 사람이 시작하고, 하위 과제는 GitHub 이슈가 나른다.
  • 캠페인 차원의 git이 없다. 캠페인 디렉터리는 커밋되지 않는다.
  • 상태 파일, 잠금 파일, 로컬 데이터베이스가 없다. 셋 다 GitHub 사실의 두 번째 사본이 된다.
  • 하트비트가 없다. 생존은 이미 herdr 사실이고, 하트비트는 에이전트가 바쁘기만 해도 멈춘다.
  • 과제 배정 메시지가 없다. 브리프는 파일이다.
  • 자기 종료가 없다. 위임자의 작업을 검증할 수 있는 것은 그 위임자가 아닌 무언가뿐이다.
  • 멤버 저장소들을 가로지르는 하나의 git 명령이 없다. 멤버 저장소의 파일은 컨테이너에 커밋하지 않는다.
  • 기계 사이의 합의가 없다. 여러 기계가 같은 캠페인을 잡아도 지역 디렉터리는 서로 같을 필요가 없다.

리뷰를 지켜보는 것도 없다. 풀 리퀘스트가 열린 시점에 에이전트가 물러나므로, 보드가 생기기 전까지는 사람이 알아채는 쪽이다. spec/alloy/ledger.als @ d6cefab
